# ADR-0008: UUID version 7 identifiers, generated in the application

- **Status:** Accepted
- **Date:** 2026-10-11
- **Deciders:** Maria

## Context

Every aggregate is identified by a typed UUID (`UserId`, `AccountId`), generated before
anything is saved so that `create(...)` can hand back a complete aggregate. Those
identifiers were version 4 — entirely random.

Random keys are the one part of this choice with a measurable cost. A version 4 value
scatters inserts across the whole primary key index: pages split, the hot set stops
fitting in cache, and on PostgreSQL the write-ahead log grows with it. The usual escape is
a database-generated `bigint` surrogate key with the UUID kept beside it as a business
key, and that was tried on `feature/create-account`. It cost more than it was worth:
identity generation forced Hibernate to insert during `save` rather than at flush, which
broke a constraint test and disabled insert batching; `save` grew upsert logic to avoid
inserting a second row for the same business key; and every row carried two identities and
two unique indexes while every lookup still went through the UUID.

Version 7 removes the reason for that trade. It is a 48-bit millisecond timestamp followed
by random bits (RFC 9562), so values are time-ordered while staying globally unique and
generated by the application.

## Decision

Identifiers are UUID version 7, generated by `common/domain/Uuid7` and used directly as
the primary key. There is no surrogate key.

`TypedUuidBase` rejects anything that is not version 7, on every path — a new identifier,
one read back from storage, one parsed from a request — so an identifier that did not come
from `Uuid7` cannot exist in the domain at all.

`Uuid7` keeps a 12-bit counter so identifiers minted inside the same millisecond are
ordered too. On counter overflow, or a clock that moves backwards, it borrows the next
millisecond rather than repeat a value.

## Alternatives considered

- **UUID version 4** — what we had. Simple (`UUID.randomUUID()`), but unordered, which is
  the cost described above.
- **A `bigint` surrogate key, UUID as a business key** — fastest keys and narrowest
  foreign keys, but two identities per row, and in this codebase it also meant eager
  inserts, no batching and upsert logic in the repository. Rejected as complexity we
  cannot justify at this scale.
- **A database sequence** — would fix the batching problem a surrogate key introduced, but
  keeps two identities and makes the application depend on the database to know what it
  just created. Also sequential integers in URLs invite enumeration.
- **A UUID version 7 library** (`com.fasterxml.uuid:java-uuid-generator`) — less code to
  own, but `core` deliberately carries almost no dependencies, and the generator is about
  forty lines.

## Consequences

Inserts land at the end of the index, as with a sequence, while identity stays the
application's to assign: aggregates are complete before they are saved, writes batch, and
nothing needs reading back after an insert.

Identifiers leak their creation time. Anyone holding one can read the millisecond it was
minted, which is public information we accept; it also means a `created_at` column is
strictly convenience, not the only record of when a row appeared.

The validation in `TypedUuidBase` is strict on purpose, and it applies when reading too. A
row carrying a version 4 identifier — written before this decision, or by hand — will fail
to load rather than load quietly. Test fixtures must use real version 7 values.

`Uuid7` is global mutable state behind a `synchronized` block. That is the price of the
monotonic counter, and it is contended only by threads minting identifiers in the same
millisecond.

The migrations on `feature/create-account` were squashed back to `V1` and `V2` rather than
reversed with a `V4`, which breaks the append-only rule in [AGENTS.md](../../AGENTS.md).
This was a deliberate exception: the branch is unmerged and the schema only ever existed
in an in-memory H2 database, so no deployed database carried it. The rule stands for every
migration from here on.
